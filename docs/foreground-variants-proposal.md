# 前景色的变体配置提案

状态：2026-11-18 已按本文实现。使用说明见 [theme-customization.md](theme-customization.md) 的 3.2 节；本文保留设计过程与各组件的取色现状。

## 当前结论

优先检查和调整应用的色板配置，使其适配组件库已有的取色规则。不能因为魔杖的一组自定义配色出现低对比度，就直接认定开源组件库需要修改渲染逻辑。

本文记录这项扩展的设计：保留 `color_foreground`，允许在 `light`、`dark` 里进一步按变体、状态、位置显式配置前景色。

没有写过字色的颜色，所有组件的外观与以前完全一致；库也不会自动改写颜色，只在对比度不足时给警告。

## 已有能力

提交 `d4d94299f6b2c002baf4cf36b7220d13f1462eb8` 已实现主题定制、实色底前景色配置与对比度告警。客户端已安装的 0.18.8 包含相关取色及检查代码。

当前支持：

```python
color_foreground={
    "primary": "#11181C",  # 实色底前景色，亮暗通用。
    "default": {"light": "#FEFEFF", "dark": "#D4D4D8"},
}
```

它控制实色底上的文字和图标，例如 Button 的 `solid`、`ghost` 悬停填充状态，以及 Alert 的 `solid`。它不代表所有组件、所有变体都统一读取这个字色。

例如，彩色 Input 的正文、浮动标签，以及 Alert 的 `flat` 正文，仍按各自规则从色阶中取色。Button 普通与悬停状态也可能使用不同背景。

现有配置检查主要比较已修改颜色的实色字色与 500 档背景；暗色 `default` 使用 700 档。它不会覆盖每个组件的每种状态，而且遵守“只提示、不改写”的既有约定。

## 候选结构

方向不变：在已有的 `light`、`dark` 里增加对象写法，不另开一套组件配置入口。

以下是候选写法，当前版本不能直接使用。示例字色不是适用于任意背景的推荐值。

### 一句话规则

一个颜色在一个主题里的字色，可以从粗到细逐层写：

```text
颜色 → 主题（light / dark） → 变体 → 状态 → 位置
```

每一层都可以直接写一个 `#RRGGBB`，也可以写成对象继续细分。没写的地方，沿用上一层的 `default`，再没有就用组件原来的取色规则。

### 四种写法，由简到繁

```python
color_foreground={
    # 写法一：和现在完全一样，一个 hex，亮暗通用。
    "primary": "#FEFEFF",

    # 写法二：和现在完全一样，亮暗分开。
    "default": {"light": "#FEFEFF", "dark": "#D4D4D8"},

    # 写法三：按变体分。
    "warning": {
        "light": {"solid": "#11181C", "flat": "#5B280A"},
        "dark": "#11181C",          # 一侧写 hex，另一侧写对象，可以混用。
    },

    # 写法四：再按状态、位置细分。
    "danger": {
        "light": {
            "default": "#FEFEFF",   # 本主题里没单独写的变体，用它。
            "flat": {
                "default": "#7A0A2E",
                "hover": "#5C0722",         # 悬停时单独换。
                "placeholder": "#A33A5C",   # 占位符单独换。
            },
        },
        "dark": {"default": "#FFD0DD"},
    },
}
```

规则：

- 对象里同时要有 `light` 和 `dark` 两个键，和现在的字典写法一致。一侧可以是 hex，一侧可以是对象。
- 亮色的配置不会自动套到暗色，两边各管各的。
- 最底层的值只能是 `#RRGGBB`，不接受 `rgb()`、颜色名、透明度。

### 能写哪些名字

名字只能从下面三张表里选，写错报错。

- **变体**（几个组件共用同名变体，同名即共享，见后面的“同名变体”）

| 名字         | 说明               |
| ------------ | ------------------ |
| `solid`      | 实色填充           |
| `bordered`   | 描边               |
| `flat`       | 半透明浅底         |
| `light`      | 透明底             |
| `faded`      | 浅灰底加描边       |
| `ghost`      | 描边，悬停时填实色 |
| `shadow`     | 实色加阴影         |
| `dot`        | 带圆点的描边       |
| `underlined` | 下划线             |

- **状态**

| 名字       | 说明         |
| ---------- | ------------ |
| `hover`    | 鼠标悬停     |
| `focus`    | 获得焦点     |
| `selected` | 选中、当前项 |
| `invalid`  | 出错         |
| `disabled` | 禁用         |

普通状态不用单独写，就是没有命中任何状态时的值，即这一层的 `default`。

- **位置**（同一个控件里不同的字）

| 名字            | 说明                       |
| --------------- | -------------------------- |
| `text`          | 正文                       |
| `icon`          | 图标                       |
| `title`         | 标题                       |
| `description`   | 说明文字、辅助文字         |
| `label`         | 标签（浮起后，或放在外面） |
| `label_resting` | 还没浮起的内部标签         |
| `placeholder`   | 占位符                     |

另外每一层都有一个特殊的键 `default`，意思是“这一层没写到的，用我”。

### 每一层里能放什么

| 层                              | 对象里可以写的键                  |
| ------------------------------- | --------------------------------- |
| 主题层（`light` / `dark` 的值） | `default`、各个变体名             |
| 变体层                          | `default`、各个状态名、各个位置名 |
| 状态层                          | `default`、各个位置名             |
| 位置层                          | 只能是 hex                        |

键放错层，比如在主题层直接写 `hover`，报错。

### 核对中发现的现状与决定

读代码时发现，有些组件的字色没有走 `color_foreground`。每一项都已定了处理方式：

| 现状                                                                                                                                                                         | 决定                                                                                |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| 灰色（`default`）的字：Tabs、分页、日历、列表和表格的行、Popover、Tooltip 直接用默认文字色，不读 `color_foreground["default"]`。原因是它们的灰色底是浅色，换成近白字会看不见 | **不动。** 新配置对这些组件的灰色不生效。Button、Chip、Alert、Avatar 的灰色照常生效 |
| Toast 的 `solid`，`success` 色的字写死成深色                                                                                                                                 | **改成读配置。** 默认值保持深色，不配的人看不出变化                                 |
| Switch 的白色圆块固定读 `primary` 的亮色字色                                                                                                                                 | **不动**（与官方 HeroUI 一致）                                                      |
| Checkbox 暗色下灰色的勾用色阶 900，不读配置                                                                                                                                  | **不动**（和上面灰色一类）                                                          |
| Input、Textarea、DateInput、InputOtp 里“文字用哪个色号”的代码各有一份，内容相同                                                                                              | **4 个文件各加几行**，让它们先查新配置，查不到再走原来的规则。不合并                |
| Input 的悬停、聚焦不改正文字色，只改边框和底色                                                                                                                               | 不处理。`flat.hover` 这类写法对 Input 不生效，但 Button 读它，所以写法合法，不警告  |
| Input 的字色现在不看变体，只看颜色                                                                                                                                           | 新键里的 `flat`、`bordered` 等对 Input 是新能力。没写时，各变体仍是原来的同一个颜色 |
| Alert、Toast 的关闭按钮、Toast 的进度条没有对应的位置名                                                                                                                      | 不新增名字，**跟随 `icon`**                                                         |
| 悬停水波纹的颜色读 `primary` 的亮色字色                                                                                                                                      | 不在字色范围内，不处理                                                              |
| Radio 的圆点、Progress 的数值字没核对到取色位置                                                                                                                              | 暂不纳入                                                                            |

### 一次取色怎么查

组件要某个字色时，带着“颜色、主题、变体、状态、位置”去查，按下面的顺序，第一个有值的就用：

1. 变体里这个状态下的这个位置
2. 变体里这个状态下的 `default`
3. 变体里这个位置
4. 变体里的 `default`
5. 主题层的 `default`（只管 `text`、`icon`、`title`，见下面）
6. 组件原来的取色规则

几点说明：

- **多个状态同时成立**时，按 `disabled`、`invalid`、`selected`、`focus`、`hover` 的顺序，先查最靠前的，查不到再查下一个。比如又 `hover` 又 `invalid`，先看 `invalid` 有没有配。
- **禁用状态不吃兜底。** 状态里有 `disabled` 时，只看明确写给 `disabled` 的值，变体层和主题层的 `default` 都不用，免得禁用的控件和正常的控件同色。旧写法（单个 hex）也不管禁用。
- **`default` 只兜 `text`、`icon`、`title`。** `placeholder`、`label`、`label_resting`、`description` 不吃 `default`，没单独写就走原来的规则。否则占位符会和正文变成同一种颜色，没法区分。
- **混用时状态比位置优先。** 比如同时写了 `flat.hover` 和 `flat.label`，悬停时 `label` 先取 `flat.hover`。不建议这样混着写。
- 写了某个键的颜色，**实例上明确传入的颜色优先于它**，比如 `Text(color=...)`、`Icon(color=...)`、`Button(icon_color=...)`。
- **按钮的图标**：只写了文字色、没写 `icon` 时，图标跟着文字色走（按钮的图标本来就跟文字对齐）。

### 和现在的写法怎么兼容

旧写法的含义不变，只管“实色底上的字”：

| 旧写法                 | 等价的新写法                                                                                                                             |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `"primary": "#FEFEFF"` | `"primary": {"light": {"solid": "#FEFEFF", "ghost": {"hover": "#FEFEFF"}}, "dark": {"solid": "#FEFEFF", "ghost": {"hover": "#FEFEFF"}}}` |

也就是说，旧的字符串不会突然变成“覆盖所有变体”。想一次覆盖所有变体，要明确写新对象里的 `default`，那是主动选择。

不改 `color_foreground` 的项目，行为和现在一模一样。

### 校验

和现有校验一样：先收集所有问题，一起报，不是遇到一个就停。

- **报错（`setup()` 里抛 `ValueError`）**

- 颜色名不是 6 个语义色之一。
- 对象里缺 `light` 或 `dark`。
- 变体、状态、位置名不在上面三张表里。
- 键放错了层，比如主题层写了 `hover`。
- 值不是 `#RRGGBB`，或写了空对象 `{}`。
- 改了 `colors` 里的色阶，却没写这个颜色的 `color_foreground`，这是现有规则，继续保留。

- **警告（只提示，不改颜色）**

- 字色和它实际所在的背景对比度不够，见下一节。
- 写了一个**所有组件都不读**的组合。因为变体、状态、位置是全组件共享的，只要有任何一个组件读它，就是合法的，不警告。比如 `flat.hover`：Button 读它，Alert、Input 不读也不要紧。会警告的是 `{"underlined": {"hover": ...}}` 这种：没有任何组件的 `underlined` 有悬停字色。

### 对比度检查扩展到哪里

现在只比较“实色字色”和 500 档背景。扩展后，对每个写了的值检查，背景按下面来取：

| 变体            | 检查时的背景                                                                  |
| --------------- | ----------------------------------------------------------------------------- |
| `solid`         | 500 档；暗色 `default` 用 700；悬停用 600                                     |
| `ghost`         | 常态是父级背景；悬停是 500 档                                                 |
| `flat`、`light` | 500 档按各自透明度叠在**父级背景**上之后的结果（亮 15%、暗 20% 起，悬停更深） |
| `bordered`      | 父级背景                                                                      |
| `faded`         | `default` 的 100（亮）或 800（暗）                                            |
| Input 系列      | 对应的输入框底色，随变体和状态变                                              |

规则：

- 正文、标题、说明、标签、占位符要求 4.5:1，图标要求 3:1。
- 禁用状态不检查；出错（`invalid`）状态的底色是 danger 色，也不检查。
- 判断时用没有四舍五入的原始数值。
- 只检查用户明确写了的值，不检查组件自己算出来的值，也不扩大到全库扫描。
- 只告警，不改写颜色。

### 完整示例

只为魔杖里常见的“亮黄色在浅底上看不清”做修正：

```python
color_foreground={
    "warning": {
        "light": {
            "solid": "#11181C",          # 实色黄底上用近黑字（对比度约 12.7:1）
            "ghost": {"hover": "#11181C"},
            "flat": {
                "default": "#5B3A00",    # 浅黄底上的字改深
                "hover": "#4A2F00",
                "icon": "#7A5300",
            },
            "light": "#5B3A00",
            "bordered": "#5B3A00",
            "faded": "#5B3A00",
            "underlined": {"placeholder": "#7A5C00", "label": "#5B3A00"},
        },
        "dark": {
            "default": "#FFE08A",         # 暗色整体用浅黄字
            "solid": "#11181C",           # 实色底（solid / shadow / ghost 悬停）上要用深色字，
            "shadow": "#11181C",          # 否则浅黄字落在橙黄底上只有 1.6:1
            "ghost": {"hover": "#11181C"},
        },
    },
}
```

没写到的颜色（`primary`、`danger` 等）、没写到的变体和状态，全部沿用原来的规则。

### 同名变体：已定，全组件共享

`flat`、`bordered`、`faded`、`solid` 这些变体名，在 Button、Alert、Chip、Input 里不一定对应同样的背景。**决定：全组件共享**，写 `"flat": "#5B3A00"` 就对所有读 `flat` 的组件生效。

- 配置里不加组件名这一层，也不校验组件名。
- 如果某个组件的 `flat` 背景特别浅或特别深，共享的字色在它那里不合适，靠上面的对比度警告发现。
- 发现问题后先调字色，让它在所有读它的组件上都够用；实在调不平，再考虑按组件拆。

按组件拆（在变体层前面加一层组件名，如 `{"Input": {"flat": ...}, "Button": {"flat": ...}}`）这次不做。它的配置更长，还要多一批组件名校验。以后真要加，是在现有写法上多开一种写法，不会改变这里已有的写法。

### 已定的决定

| 事项                                   | 决定                                                                     |
| -------------------------------------- | ------------------------------------------------------------------------ |
| 同名变体                               | 全组件共享，不加组件名这一层                                             |
| 状态优先级                             | `disabled > invalid > selected > focus > hover`                          |
| Select、Autocomplete、DatePicker       | 不新增键，完全跟随内部的 Input / DateInput                               |
| `shadow`、`dot` 等只有个别组件用的变体 | 进全局变体名单，统一校验；只要有一个组件读它就合法，其余组件不读，不影响 |
| 灰色字                                 | Tabs、分页、日历等浅底组件的灰色不动，见上表                             |
| 输入框 4 份代码                        | 各自加几行，不合并                                                       |
| 关闭按钮、进度条                       | 跟随 `icon`                                                              |
| 警告规则                               | 只对“所有组件都不读”的组合警告                                           |
| 实施时要补的测试                       | 旧写法行为不变、各层兜底顺序、校验报错与警告、亮暗各自独立、实例参数优先 |

## 色板问题应先排查

用户认为可以通过为亮色模式配置更浓、更饱和的颜色来改善可读性。后续工作应首先验证这个方向，同时检查明度，而不是把修改组件库作为默认前提。

饱和度增加可能改变对比度，但不能单独保证可读。亮黄本身可以具有很高的饱和度和亮度；提高饱和度后仍可能与浅底接近。应同时控制色相、饱和度和明度，并测量最终前景与实际背景的组合。

下面是基于当前魔杖配色的计算示例，固定背景为 `#FFF7D8`。饱和度和明度使用 HSL 表示；对比度按 sRGB 相对亮度计算。

| 前景色                       | HSL 饱和度 | HSL 明度 | 对比度 |
| ---------------------------- | ---------- | -------- | ------ |
| 原亮黄 `#FDD704`             | 98.42%     | 50.39%   | 1.31:1 |
| 仅提高饱和度 `#FFD802`       | 100%       | 50.39%   | 1.30:1 |
| 更深且满饱和的金色 `#806A00` | 100%       | 25.10%   | 4.91:1 |

这说明可以优先调整应用配色，但“只提高饱和度”与“同时把文字颜色调深”不是同一种调整。上述颜色只是说明这个差异，不代表现有组件会自动取用这个示例色。

亮黄作为实色填充仍然可用：`#11181C` 文字在 `#FDD704` 背景上的对比度约为 12.72:1。不能把某个浅底文字组合失败，理解成黄色整体不能使用。

## 后续验证顺序

1. 使用实际发行包确认组件从哪一档取背景、正文、标签和状态色。
2. 优先调整色板及现有配置，并验证亮色、暗色与实际父级背景；不能只验证实色按钮普通态。
3. 透明背景先与父级背景合成，再计算普通、悬停、聚焦等状态的对比度。数值判定使用原始结果，不先四舍五入。
4. 对仍然不合格且无法通过配色解决的组合，列出组件、主题、变体、状态、颜色来源和对比度，再决定是否需要新增配置能力。
5. 如需实现扩展，先确认上述兼容性问题，再增加覆盖规则和回归测试。默认色板和未配置覆盖的旧调用应维持原行为。

参考：[WCAG 2.2 文字对比度说明](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)。普通文字最低要求通常为 4.5:1；完整无障碍验证还包括图标、焦点指示等其他项目。
