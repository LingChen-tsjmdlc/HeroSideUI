# 主题定制：颜色、圆角、阴影、字体

状态：设计已于 2026-11-16 确认，**代码已于 2026-11-16 实现完成**（实现中与设计的出入见第 10 节"实现记录"）。测试已写好但未运行，由项目维护者运行。仍有若干项待看真实窗口后定（见第 8 节），其余以本文为准。

## 1. 目标

默认设计语言是 HeroUI v2。用户可以在 `HeroSideUIProvider.setup()` 里直接改色板、圆角、底色、文字色、阴影和字体字号，不需要额外的配置文件。

原则：

- 配置只写在 `setup()` 的调用处，不引入配置文件，也不提供 `default_values()` 这类读取默认值的新 API。
- 写了哪一组就必须把这一组写全，不自动生成、不补全。没写的组保持默认。
- 全部是 keyword-only 新参数，现有参数一个不动，旧调用不受影响。
- 只做启动时配置。组件创建之前调用 `setup`，组件创建时读到的就是新值。
- **默认值里不出现纯黑 `#000000` 和纯白 `#FFFFFF`**，一律略微偏一点点。纯黑纯白在屏幕上显得生硬，也和库整体的偏冷色调不搭。这条只约束库自己的默认值；用户自己写的值不受限制。

| 原来                    | 现在                                           | 用在哪                                       |
| ----------------------- | ---------------------------------------------- | -------------------------------------------- |
| `#FFFFFF`               | `#FEFEFF`（近白，带一丝冷调）                  | 亮色弹出层底；实色底上的字；暗色阴影的内描边 |
| `#000000`（字）         | `#11181C`（与默认文字色同一个值）              | warning 黄底上的字                           |
| `#000000`（阴影、遮罩） | `#020304`（近黑，比暗色窗口底 `#0D0D0F` 更暗） | 所有阴影的颜色、模态遮罩                     |

对比度几乎没变（白字：primary 4.66 变 4.62，secondary 7.15 变 7.10；warning 黑字 10.29 变 8.79，仍远高于 4.5）。三层底色的层级见 3.4 的“三层底色怎么搭”。

## 2. 参数总览

`setup` 新增 10 个参数，另有 2 个已有参数语义调整：

| 参数                     | 写法                                             | 默认                   | 管什么                          |
| ------------------------ | ------------------------------------------------ | ---------------------- | ------------------------------- |
| `colors`                 | `{色名: 10 个 hex 的列表或字典}`                 | HeroUI v2 色板         | 6 个语义色的 50~900 色阶        |
| `color_foreground`       | `{色名: "#hex" 或 {"light","dark"}}`             | 近白字，warning 深色字 | 实色底上的文字 / 图标色         |
| `radius`                 | `{"sm","md","lg"}` 整数 px                       | 4 / 8 / 14             | 三档圆角                        |
| `background`             | `{"light","dark"}` hex                           | `#FAFBFD` / `#0D0D0F`  | 窗口底色                        |
| `foreground`             | 同上                                             | `#11181C` / `#ECEDEE`  | 所有文字、图标默认色            |
| `content_background`     | 同上                                             | `#FEFEFF` / `#18181B`  | 内容面底色（Card 等）           |
| `popup_background`       | 同上                                             | `#FEFEFF` / `#27272A`  | 弹出层底色（Popover 等）        |
| `shadow`                 | `{"light","dark"}` × `{"sm","md","lg"}` × 层列表 | 官方 HeroUI 三档       | 阴影                            |
| `mono_family`            | 字体名或字体文件路径                             | 内置 Maple Mono        | 代码字体                        |
| `font_size`              | `{"xs","sm","md","lg","xl"}` 整数 px             | 10 / 13 / 16 / 19 / 22 | 五档字号                        |
| `font_family`（已有）    | 字体名或字体文件路径                             | 内置思源黑体           | 正文字体，新增路径写法与校验    |
| `font_base_size`（已有） | 整数 px                                          | 16                     | 收敛为 `font_size["md"]` 的简写 |

### 完整示例：全部写成默认值

## 3. 各参数说明

### 3.1 colors

- 写法一：10 个 hex 的列表，按 50 到 900 的顺序，一个色一行。写法二：`{50: "...", ..., 900: "..."}`。两种等价。
- 色名只有 6 个：`default`、`primary`、`secondary`、`success`、`warning`、`danger`，不能新增色名。库里原有的 `neutral`（纯灰）色阶已删除，见本节末尾。
- 写了哪个色，这个色就必须 10 阶写全。hex 只接受 `#RRGGBB`。
- 暗色不用另写：库里暗色是把亮色阶按索引镜像反转（50 对 900，100 对 800……），所以亮色阶必须从浅到深。不满足时只给警告，不报错。

**注意：`default`（灰色）比其他色影响大。**

`primary`、`secondary`、`success`、`warning`、`danger` 这 5 个色，只影响用到它们的组件。比如改 `primary`，只有蓝色按钮、蓝色链接这类东西会变。

`default` 不一样，它有两个身份：

1. 它是一个普通的颜色名，`Button color="default"` 就是用它。
2. 它还是全库所有"灰色"的来源：分隔线、边框、次要文字、占位文字、鼠标悬停（hover）的底色，都是从它取的。全库有 41 个文件直接用到它。

所以改 `default`，变的不只是灰色按钮，而是全库每一处灰色。比如你把它换成偏暖的灰，分隔线、边框、说明文字都会跟着变暖；换成偏蓝的灰，它们都会偏蓝。想让整个界面的灰调统一换味道，改它一处就够了；不想动这些，就别改它。

#### 怎么改 `default`

写法和 `primary` 完全一样：写在 `colors` 里，一个色 10 个值，按 50、100、200……900 的顺序。它不是从 `background`、`foreground` 等参数算出来的，也不会算出它们。

```python
HeroSideUIProvider.setup(
    app,
    colors={
        # 暖灰（Tailwind stone）
        "default": ["#fafaf9", "#f5f5f4", "#e7e5e4", "#d6d3d1", "#a8a29e",
                    "#78716c", "#57534e", "#44403c", "#292524", "#1c1917"],
    },
    # 改了 default 就必须写它的字色（3.2 的规则）
    color_foreground={"default": {"light": "#FEFEFF", "dark": "#D4D4D8"}},
)
```

默认的 `default` 是下面这 10 个值（偏冷的灰），可以对着它改：

| 50        | 100       | 200       | 300       | 400       | 500       | 600       | 700       | 800       | 900       |
| --------- | --------- | --------- | --------- | --------- | --------- | --------- | --------- | --------- | --------- |
| `#fafafa` | `#f4f4f5` | `#e4e4e7` | `#d4d4d8` | `#a1a1aa` | `#71717a` | `#52525b` | `#3f3f46` | `#27272a` | `#18181b` |

两点规则：

- 必须从浅到深排。分隔线和次要文字在暗色下靠镜像反转取色，排乱了暗色会反相。
- 改了它，必须同时写 `color_foreground` 里的 `default`，否则报错。

#### 改完 `default` 不会联动的东西

`default` 只管"灰色的色阶"。下面这些是各自独立的参数，**你改了 `default`，它们不会跟着变**：

| 参数                 | 管什么                 |
| -------------------- | ---------------------- |
| `background`         | 窗口最底层的背景色     |
| `foreground`         | 默认文字色             |
| `content_background` | Card 这类"面"的底色    |
| `popup_background`   | 弹出层的底色           |
| `color_foreground`   | 实色按钮上的字是黑是白 |

举个容易踩的例子：默认值下，暗色的 `content_background`（`#18181B`）恰好等于 `default` 的第 900 档。但改了 `default` 之后，它们是两回事：你把 `default` 换成暖灰，分隔线和说明文字会变暖，Card 的暗色底仍是冷的 `#18181B`。想要整套都是暖色，要自己把 `background`、`content_background`、`popup_background` 也一起改成暖色。这是"不自动生成、你自己写"的结果。

#### `neutral` 已删除

库里原来还有一组 `neutral`（纯灰），只给两处用：滚动条的默认颜色，和 Textarea 右下角的拖拽柄。它和 `default` 只差一点点（`default` 是微蓝的灰，`neutral` 是纯灰），却多出一个色名要用户去认，而且用户换了 `default` 之后，滚动条还停在纯灰上，对不上。所以删掉，这两处改用 `default`：

| 位置               | 原来                                     | 改为                                     | 颜色变化     |
| ------------------ | ---------------------------------------- | ---------------------------------------- | ------------ |
| 滚动条把手（亮色） | neutral 300 / 400：`#d4d4d4` / `#a3a3a3` | default 300 / 400：`#d4d4d8` / `#a1a1aa` | 极小，略偏蓝 |
| 滚动条把手（暗色） | neutral 700 / 600：`#404040` / `#525252` | default 700 / 600：`#3f3f46` / `#52525b` | 极小，略偏蓝 |
| Textarea 拖拽柄    | neutral 400 / 500：`#a3a3a3` / `#737373` | default 400 / 500：`#a1a1aa` / `#71717a` | 极小，略偏蓝 |

好处：用户改 `default` 灰调，滚动条和拖拽柄跟着变，整套灰统一。

删除要改的地方（全仓核查过）：

- `themes/colors.py`：删除 `neutral` 色阶和文件头注释里的说明。
- `core/scroll_style.py`：`VALID_COLORS` 去掉 `neutral`；全局默认色由 `"neutral"` 改为 `"default"`；相关注释更新。滚动条阴影边框的触发条件是"使用全局色"，不依赖 `neutral` 这个字符串，所以那套逻辑不用改。
- `components/textarea/_styling.py`：拖拽柄颜色改取 `default`；`_resize_grip.py` 里写着 `neutral-400` 的注释更新。
- `components/pagination/_constants.py`、`components/table/_constants.py`：`VALID_COLORS` 里的 `k != "neutral"` 过滤不再需要，去掉。
- `components/radio/_base.py`：`VALID_COLORS = tuple(HEROUI_COLORS.keys())` 现在会错误地接受 `color="neutral"`，删掉 `neutral` 后顺带修正。
- 文档：`scroll_style.md`、`textarea.md`、`text.md` 里提到 `neutral` 的地方；`code_block.md` 写着"代码区底色用 neutral-100 / neutral-800"，但代码实际取的是 `default` 的 50 / 900，文档本来就是错的，一并更正，`code_block.py` 里的两处 `neutral` 注释同步更正。
- 示例与测试：`examples/text/demo.py` 的色名列表去掉 `neutral`；`tests/core/test_scroll_style.py`、`tests/components/test_textarea.py` 里 `neutral` 的断言改为 `default` 的值。

**对外可见的不兼容变更**（发版说明里写明）：

- `ScrollStyle.set_color("neutral")` 以后抛 `ValueError`，改用 `"default"`。
- `Text(color="neutral-500")` 这类色名写法以后不再识别，改用 `"default-500"`。
- 滚动条把手、Textarea 拖拽柄的默认颜色有上表所列的极小变化。

### 3.2 color_foreground

指 solid 按钮、实色 Chip、Alert、Avatar、Toast 等"实色底上的文字 / 图标"的颜色。官方 HeroUI 按 500 档底色自动算黑字或白字，本库不自动算，改成显式配置。

| 色                                     | 亮色      | 暗色                                                  |
| -------------------------------------- | --------- | ----------------------------------------------------- |
| primary / secondary / success / danger | `#FEFEFF` | `#FEFEFF`                                             |
| warning                                | `#11181C` | `#11181C`                                             |
| default                                | `#FEFEFF` | `#D4D4D8`（暗色下 default 实色底用 700 档，不是 500） |

```python
color_foreground={
    "primary": "#FEFEFF",                                # 一个 hex：亮暗通用
    "default": {"light": "#FEFEFF", "dark": "#D4D4D8"},  # 字典：亮暗分开
}
```

规则：

1. **改了 `colors` 里某个色，就必须在 `color_foreground` 里写它**，否则报错。色阶一变，原来的白字可能就看不清，不能悄悄沿用。
2. 没改色阶的色保持上表默认；也允许只改字色不改色阶。
3. 只提示、不改写：用户写的字色与底色（500 档，暗色下的 default 用 700 档）对比度低于 4.5:1 时给警告，写明实际比值。**只检查用户传入的值，不检查库的默认值**：默认值里 success 白字只有 2.18:1、danger 4.11:1，本来就低于 4.5，这是 HeroUI 沿用至今的外观，不在本次改动范围。
4. 统一入口 `get_color_foreground(color, theme)`，所有位置改成走它。

### 3.3 radius

- 组件的 `radius="lg"` 是档位名，永远不变；`setup` 里的 `"lg": 10` 是这个档位的像素值。名字固定、数值可配，不存在"预设档冲突"。
- `sm`、`md`、`lg` 三个必须全写，值是非负整数，要求 `sm <= md <= lg`。
- `none` 恒为 0，`full` 按高度动态算，两者不可配。
- 内部的 `no/small/medium/large` 长名别名现在是 import 时复制的字符串，必须随之同步。

### 3.4 四个面与文字色

写法一致：`{"light": "#RRGGBB", "dark": "#RRGGBB"}`，亮暗都要写。

| 参数                 | 含义                                       | 谁在用                                                                                 |
| -------------------- | ------------------------------------------ | -------------------------------------------------------------------------------------- |
| `background`         | 窗口底色，页面最底层                       | `ThemeProvider` 同步到 `QApplication` 的 `Window` 调色板                               |
| `foreground`         | 所有文字、图标的默认色，含 `Text` 默认字色 | 所有组件；`ThemeProvider` 同步到 `WindowText`                                          |
| `content_background` | 内容面，浮在窗口上的"面"                   | Card、Toast、Radio 卡片、Accordion、Drawer、Calendar 头部                              |
| `popup_background`   | 弹出层，浮在内容面上的层                   | Popover、Tooltip、Slider 浮标，以及基于 Popover 的 Dropdown、Select、Autocomplete 弹层 |

要点：

- `content_background` 对应官方 content1；官方 content2~4 是 hover、层叠用的，仍从 `default` 色阶取，不开放。
- `popup_background` 是桌面端的有意偏离：官方 Popover 与 Card 同色，本库暗色下弹层比 Card 亮一档，贴在 Card 上才分得出层级。不叫 `overlay`，官方里它是模态遮罩的 `#000`。
- 暗色下层级靠"窗口底 < 内容面 < 弹层"逐级变亮，改暗色值时三个要一起看。
- Card 暗色底原来是 `default[900]`，改后走 `content_background`：默认值相同，但此后不再跟随 `default` 色阶，一个来源、一个入口。
- 所有文字统一用 `foreground`，不做"每层各自的前景色"。

#### 三层底色怎么搭（窗口底 → Card → 弹出层）

**先说结论（建议）：亮色三层这样定，层次交给阴影，不靠底色。**

| 主题         | 窗口底    | Card      | 弹出层    | 靠什么分开                                                              |
| ------------ | --------- | --------- | --------- | ----------------------------------------------------------------------- |
| 亮色（建议） | `#FAFBFD` | `#FEFEFF` | `#FEFEFF` | 窗口与 Card：略灰对近白，加阴影；Card 与弹出层：同色，靠阴影和 1px 细线 |
| 暗色         | `#0D0D0F` | `#18181B` | `#27272A` | 底色逐级变亮                                                            |

暗色窗口底由库原来的 `#0B0D12`（带青蓝，色相 268°）改为 `#0D0D0F`（色相 286°），与 Card、弹出层、`default` 灰阶的边框和悬停色统一到同一个灰调上，整体不再偏青蓝。明度几乎不变。实现时 `theme_provider.py` 里写着“偏冷一点 `#0B0D12`”的注释和值一起改掉。

这和原版 HeroUI 的思路一致：原版亮色下三层都是同一个纯白，分层全靠阴影。我们只是把纯白换成近白，并保留库原来略灰的窗口底。

**为什么亮色不靠底色分层。** 库里输入框、灰色按钮、悬停底色这些"灰色填充"，亮色下都取 `default-100`（`#f4f4f5`）。它要看得清，所在的底色就不能和它太近：

| 灰填充放在哪 | 底色                                | 明度差（3 以上才清楚） |
| ------------ | ----------------------------------- | ---------------------- |
| Card 上      | `#FEFEFF`（建议）                   | 3.5                    |
| 窗口上       | `#FAFBFD`（建议）                   | 2.4                    |
| 窗口上       | `#F1F3F6`（曾试过的新默认，已放弃） | **−0.4**，几乎隐形     |
| 窗口上       | `#E9ECF1`（方案 A）                 | 2.9，勉强              |

想用底色把三层都拉开，窗口底就得降到跟灰填充撞色；想避免撞色，就要把全库 24 处灰填充改深（方案 B），输入框整体变重，外观变动太大。所以沿用原版思路。

**这个建议的代价，直说：** 亮色下 Card 上弹出的层和 Card 是同一个颜色，只靠阴影和 1px 细线分开。如果你在意"颜色必须分得开"，可改选：

- 方案 A：窗口底降到 `#E9ECF1`，弹出层额外加描边。窗口与 Card 更分明，但输入框在窗口上偏弱（2.9）。
- 方案 B：窗口底 `#F1F3F6`、Card `#F8F9FB`、弹出层 `#FEFEFF`，同时把灰填充改成 `default-200`。三层颜色都不同，但输入框整体变深。

对比页面见 `.workbuddy/scratch/light_scheme_compare.py`（五列：原版 HeroUI、近白原版、库旧默认、A、B）。

暗色没有这个问题：暗色下三层明度差是 4.7 和 7.4，靠底色就够。暗色的阴影本来就只能"若隐若现"，窗口底已接近黑，阴影最多压暗到 0；官方暗色也是靠 1px 白色内描边表现边缘，不靠阴影。

改这三个值时，规则是：**从底往上，每一层都不能比下一层更暗**（允许相等）。用户写错顺序时只给警告，不报错。

Toast 该算哪一层，见第 8 节。

### 3.5 shadow

#### 数据格式

阴影和圆角一样是全库公共的配置。官方 HeroUI 的阴影每档是 3 层叠加（远处柔光、近处投影、1px 边线），所以每档是"层列表"：

```python
shadow={
    "light": {
        "sm": [
            {"y": 0, "blur": 5,  "color": "#020304", "opacity": 0.02},
            {"y": 2, "blur": 10, "color": "#020304", "opacity": 0.06},
            {"y": 0, "blur": 1,  "color": "#020304", "opacity": 0.30},
        ],
        "md": [...], "lg": [...],
    },
    "dark": {"sm": [...], "md": [...], "lg": [...]},
}
```

规则：

1. 亮暗分开，各 `sm/md/lg` 三档都要写全。阴影色可配（每层有 `color`）。
2. 每档 1 到 4 层；每层 `y`（下偏移）、`blur`（CSS 模糊半径）、`color`、`opacity`（0 到 1）。
3. 可选 `"inset": True`，表示画在边框内侧的 1px 描边（暗色默认值用它）。
4. `none` 恒为无阴影。不支持 x 偏移和 spread（官方默认值都是 0）。
5. 组件的 `shadow="md"` 是档位名，永远不变；Card、Image、Kbd、Popover、Tooltip、Toast、Slider 浮标、Switch 滑块共用这一套值。

#### 默认值（取自官方 HeroUI `default-layout.ts`）

每项依次为 `y / blur / opacity`，外阴影统一用近黑 `#020304`，暗色的 inset 层用近白 `#FEFEFF`。

| 档  | 亮色                               | 暗色                                     |
| --- | ---------------------------------- | ---------------------------------------- |
| sm  | `0/5/.02`、`2/10/.06`、`0/1/.30`   | `0/5/.05`、`2/10/.20`、inset `0/1/.15`   |
| md  | `0/15/.03`、`2/30/.08`、`0/1/.30`  | `0/15/.06`、`2/30/.22`、inset `0/1/.15`  |
| lg  | `0/30/.04`、`30/60/.12`、`0/1/.30` | `0/30/.07`、`30/60/.26`、inset `0/1/.15` |

#### 为什么要统一并换渲染

现状没有公共阴影，有 6 处互不相干：

| 位置                     | 格式                               | 备注                                        |
| ------------------------ | ---------------------------------- | ------------------------------------------- |
| `CARD_SHADOWS`           | offset_y / blur / opacity          | 注释写"对齐 shadow-small"                   |
| `IMAGE_SHADOWS`          | 同上                               | 数值与 Card 不同                            |
| `KBD_SHADOW`             | 同上                               | 注释写"与 Card sm 同源"，实际是复制了一份数 |
| `POPOVER_SHADOWS`        | layers / blur / offset_y / alpha   | 多层叠加，Tooltip 也用它                    |
| `TOAST_SHADOWS`          | 同 Popover 格式                    | 数值与 Popover 不同                         |
| Slider 浮标、Switch 滑块 | 模块常量 / 写死 `QColor(0,0,0,35)` | 不在任何表里                                |

Chip、Button 的 `shadow` 变体是带色阴影，由语义色派生，不在此列；ScrollShadow 是渐隐遮罩，不是阴影。

现有 lg 阴影质量差，根因在画法（代码分析，尚未在屏幕上复核），换数值解决不了：

1. Card 用一圈圈放大的圆角矩形叠出模糊，每圈 alpha 取整。lg 最大 alpha 约 30，分到 15 圈上每圈只有 2 左右，取整后是一层层台阶，不是平滑渐变，衰减也不是高斯。
2. 外扩预留 `blur/2 + offset + 2`，lg 只有 25px，30px 的模糊尾巴被截断。
3. 官方 lg 是三层、最大 `0 30px 60px`；本库 lg 只有一层 `blur 30, offset 8`，体量差一倍。

#### 渲染方案

统一渲染函数 `paint_shadow(painter, rect, radius, layers)` 与 `shadow_margin(layers)`，放在 `core/shadow_paint.py`。模糊只在缓存未命中时发生，每次绘制只是贴图：

| #   | 做法                                                           | 作用                                                                  |
| --- | -------------------------------------------------------------- | --------------------------------------------------------------------- |
| 1   | 一档的所有层预合成一张图                                       | 绘制成本不随层数增加                                                  |
| 2   | "挖空本体"烘焙进缓存图，运行时不设裁剪路径                     | 抗锯齿裁剪原来占单次绘制约 65%；半透明本体下也不透出阴影，与 CSS 一致 |
| 3   | 九宫格拉伸：本体够大时，一张固定图切成 4 角 + 4 边拼出任意尺寸 | 缩放、动画不重新模糊                                                  |
| 4   | 缓存键 = 档位层内容 + 圆角 + 像素密度                          | 同档位全库共用；高分屏分别缓存                                        |
| 5   | 按字节限额的 LRU，默认 32MB                                    | lg 在 2 倍屏下单张近 3MB，按张数管不住内存                            |
| 6   | 暗色内描边用一次 1px 描边绘制                                  | 避免每次做路径相减                                                    |

九宫格最小本体边长 `t = 2 × (max(圆角, 模糊 + |y|) + 2)`，小于它时按实际尺寸整张合成并缓存。三档的 `t`：sm 32px、md 68px、lg 184px。模糊用 Qt 自带实现，不新增依赖（项目没有 numpy）；Qt 模糊半径 × 0.45 ≈ CSS 的 σ，是实测标定的系数。

#### 实测数据（离屏环境，不是真实窗口）

| 项目                             | 原型第一版 | 当前方案                                                     |
| -------------------------------- | ---------- | ------------------------------------------------------------ |
| 单次绘制，md、120×70             | 0.178 ms   | 0.025 ms                                                     |
| 单次绘制，md、400×300 / 1200×800 | 未测       | 0.076 / 0.166 ms                                             |
| 120 个面板整屏重绘（亮色）       | 42 ms      | 14 ms，其中阴影净增约 0.05 ms/个                             |
| 缩放动画，60 个面板每帧都变尺寸  |            | 13 ms/帧；逐控件 `QGraphicsDropShadowEffect` 为 23 ms/帧     |
| 冷启动合成一档                   |            | 1 倍屏 sm 1.3 / md 3.2 / lg 14.7 ms；2 倍屏 2.9 / 10 / 47 ms |
| 九宫格与整张合成的差异           |            | 最大 alpha 差 5/255，本体内 alpha 为 0                       |

说明：`QGraphicsDropShadowEffect` 在"内容不变的静态重绘"里并不慢（Qt 会缓存），选九宫格的理由是尺寸变化和动画时不重新模糊，以及 effect 会把整棵子树离屏渲染、破坏子控件自带的 effect（如 Button 的按压缩放）。缩放动画的 13 ms 含面板自身的绘制，未单独拆出阴影。

已知限制：

- 本体小于 `t`（如 lg 小于 184px）又带尺寸动画时，每个新尺寸要合成一次，2 倍屏下 lg 约 47ms 会掉帧。小控件应使用 sm 或 md。不影响静态显示和位移动画。
- 首次出现某档位有一次性冷启动成本，在 `setup()` 里预热当前主题三档。
- 窗口拖到不同缩放的显示器上，会各合成一次。

#### 阴影不占布局位置

现状：阴影留白算进控件自身尺寸，档位越大留白越大，卡片间距随档位变大，也没法与无阴影控件边缘对齐。CSS 的 box-shadow 不占位置，本库对齐这一点。

| 控件类型                                         | 做法                                                                                                                                                                                                                               |
| ------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 在布局里的控件（Card、Image 等）                 | 控件尺寸就是本体尺寸。阴影由附着的 `ShadowLayer` 绘制：挂在目标最近的“裁剪边界”（滚动区视口或窗口）下、叠在目标上方的透明覆盖层，不进布局，鼠标穿透，几何 / 显隐 / 层级跟随目标（监听 Move / Resize / Show / Hide / ZOrderChange） |
| 独立浮窗（Popover、Tooltip、Toast、Slider 浮标） | 本身是透明顶层窗口，留白在窗口内、不参与布局；只把留白换成统一的 `shadow_margin`                                                                                                                                                   |
| Kbd                                              | 同 Card：挂一个兄弟阴影层（sm 档）                                                                                                                                                                                                 |

`ShadowLayer` 的边界，与 CSS `overflow` 一致：包着目标的普通容器不裁阴影，只有滚动区视口和窗口裁（贴窗口边的卡片那一侧会被截断，需给外层留边距）；本体区域在缓存图里已挖空，阴影盖在目标上方也不会遮住它；同一窗口里相邻卡片的阴影会轻微落在邻居边缘上，和 CSS 里“后面的元素盖住前面的阴影”略有不同，差别很小。

受影响最大的是 Card（外层布局四周留 `shadow_margin`，外壳 = 内容 + 2×留白；Table 外壳复用 Card，同受影响）和 Image（wrapper = 图片 + 留白）。**Card 内部凡依赖"外壳 = 内容 + 留白"的代码（`resizeEvent`、尺寸提示、磨砂快照、按压缩放）都要核对，这是整个重构风险最高的一处。**

原型：`.workbuddy/scratch/shadow_prototype.py`（临时文件，实现时以它为基础，之后移除）。

外观变化（已确认）：Card、Image、Kbd、Popover、Tooltip、Toast 全部共用官方默认值，外观比现在更接近官方，浮层阴影体量变大，lg 变化最明显。

### 3.6 字体与字号

开放三项：正文字体、代码字体、字号档位。字重、行高、字距、`2xl` 及以上的标题字号、hinting 不开放（原因见 3.8）。

#### 现状

1. `font_base_size` 几乎不起作用：它只在"不传字号"时给 `make_qfont` 当默认值，`Text` 的 `SIZE_MAP` 写死，各组件字号写在各自预设里。
2. 字号零碎：预设共 126 个字号条目，有 10、11、12、13、14、15、16、18、19 九种取值。
3. 代码字体另成一套：`_shared/code/font.py` 默认内置 Maple Mono，失败回退 Consolas；Markdown 行内代码又单独写死 `Consolas`。

#### 设计

**字号档位：xs 10 / sm 13 / md 16 / lg 19 / xl 22，步长 3。** 依据是视觉判断：组件 `sm / md / lg`（13 / 16 / 19）层级更分明，与现有 Button 一致，经多人看过对比图后确定。

- 档位名与 `Text(size=...)`、组件的 `size=` 同名。全库统一，没有"档位加偏移"，各组件字号直接取档位；用户把 `sm` 改成 14，所有 `sm` 档文字一起变。
- 规则同 `radius`：五档全写，整数 px，要求 `xs <= sm <= md <= lg <= xl`，范围 8 到 28。`2xl`~`9xl`（24~128）保持常量。
- 与官方的关系：官方只有 `tiny 12 / small 14 / medium 16 / large 18` 四档（步长 2）。本库是桌面端修正，数值不同。想要官方数值的用户写：`font_size={"xs": 12, "sm": 14, "md": 16, "lg": 18, "xl": 20}`，用户文档要给出这一行。

`Text` 的默认字号随档位变化，这是对外可见的破坏性变更：

| `Text(size=...)` | 现在 | 默认之后 | 变化 |
| ---------------- | ---- | -------- | ---- |
| `xs`             | 12   | 10       | −2   |
| `sm`             | 14   | 13       | −1   |
| `md`             | 16   | 16       | 不变 |
| `lg`             | 18   | 19       | +1   |
| `xl`             | 20   | 22       | +2   |

库当前是 v0.8.1，未到 1.0，接受该变更；发版说明里写明，并给出上面的一键还原配置。

**字体：** `font_family`、`mono_family` 的值可以是已安装的字体名，也可以是 `.ttf` / `.otf` 文件路径（存在则先注册再使用，随应用分发字体、不依赖对方电脑是否安装）。字体名不存在或文件注册失败时报错并写明原因，不再静默回退。`mono_family` 取代 `_shared/code/font.py` 的内置默认逻辑和 Markdown 写死的 `Consolas`，CodeBlock、CodeEditor、Markdown 行内代码统一从它取（Kbd 用的是正文字体，不属于代码字体），默认仍是内置 Maple Mono。换成非内置的 `font_family` 后字重路由失效（见 `font_provider.md`），用户文档要写明。

**`font_base_size`：** 收敛为 `font_size["md"]` 的简写。只传它时只改 `md` 档并校验单调；与 `font_size` 同时传且不一致则报错。这是行为变化：以前几乎无效，现在会带动全库 `md` 档文字。

#### 已知限制：100% 缩放下小字号汉字的笔画粗细不匀

16px 的思源黑体一条笔画只有约 1.15 个物理像素，屏幕只能画整数像素，所以同一个字里有的横画实、有的虚。这是像素网格的限制，不是 bug：关闭 hinting（现状）保住了笔画真实厚度，但各笔画落在不同的亚像素位置；打开 hinting 则吸附成 1px 或 2px，更不均。抗锯齿方式（LCD 或灰度）、字体引擎都不改变结论。

实测（Windows、100% 缩放，样本为"正三王工士"的横画）：发虚笔画占比 10px 85%、12px 36%、13px 62%、14px 23%、16px 31%、19px 及以上 0%。缩放 150% 以上基本均匀。

处理：**暂不处理，文档注明。** 建议高分屏用户使用 125% 以上缩放。本方案的 `xs 10` 和 `sm 13` 恰好落在 100% 缩放下最不均的字号上，选定字号档位时要知道这一点。

#### 预设吸附结果（已按预设逐项统计）

现有预设 126 条字号，吸附到最近档位后，**69 条变化、57 条不变，预设里每条变化都恰好 1px**。

| 现有   | 10  | 11  | 12  | 13  | 14  | 15  | 16  | 18  | 19  |
| ------ | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 吸附到 | 10  | 10  | 13  | 13  | 13  | 16  | 16  | 19  | 19  |
| 变化   | 0   | −1  | +1  | 0   | −1  | +1  | 0   | +1  | 0   |

变化较多的组件（变化条数 / 总条数）：Input 8/15、Textarea 8/15、Listbox 7/9、Accordion 5/9、Progress 5/12、Table 4/6、Slider 4/9，其余 1 到 3 条。预设里的 `500`、`600` 是字重，不参与吸附。

### 3.7 不由参数控制的颜色

按下表归位，不新增参数。原则：**中性色全部从 `default` 色阶派生，语义色全部从对应色阶取，组件里不允许写 hex 字面量。**

| 颜色                      | 归属                                                                                       |
| ------------------------- | ------------------------------------------------------------------------------------------ |
| 分隔线、边框、快捷键边框  | `default` 色阶（现状已是）                                                                 |
| 次级文字、占位文字、label | `default` 色阶（见 5.1）                                                                   |
| hover / 按下色            | `default` 色阶派生（官方 content2~4 也是如此）                                             |
| 选区高亮底                | `primary[500]` 加透明度（现状已是）                                                        |
| 模态遮罩                  | 恒为黑色透明度，不可配（官方 overlay 是 `#000`，这里按“默认值不用纯黑”改用近黑 `#020304`） |
| 焦点环                    | 取 `primary[500]`（实现前先查各组件现状）                                                  |
| 代码高亮配色              | 另一套语法配色，不在本次范围                                                               |

hover 色的一处影响：`state_palette.py` 里菜单 hover 色按"暗色弹层底 = `#27272a`"标定，默认的 `popup_background` 暗色值恰好等于 `default[800]`。用户把 `popup_background` 或 `content_background` 改得明显偏离时，hover 色可能不协调，可通过改 `default` 色阶来调。用户文档写一句说明，代码不动。

### 3.8 不开放的项

| 项                          | 原因                                                                 |
| --------------------------- | -------------------------------------------------------------------- |
| 字重                        | 6 档与内置字体的物理 instance 一一对应，开放只会配出看不出区别的档位 |
| 行高                        | Qt 标签的行高由字体度量决定，没有 CSS 那种独立的 line-height         |
| 字距                        | 本库没有字距属性，中文场景几乎不用                                   |
| `2xl`~`9xl`                 | 标题级字号，由使用方显式传 `Text(size=...)`                          |
| hinting                     | 全局固定关闭，是渲染质量决策                                         |
| 模态遮罩色、disabled 透明度 | 不是风格偏好                                                         |

## 4. 生效规则

1. **先校验、后生效。** 任何一项不合法，整个 `setup` 抛一个 `ValueError`，一次列出所有问题，不会出现配置一半生效。
2. **幂等。** 每次调用 `setup` 都先把全部主题取值还原为默认值，再应用本次参数，多次调用不叠加；没写的参数回到默认值。`teardown()` 同样还原。
3. **时机。** 在 `ThemeProvider` 初始化之前应用，首屏底色就是对的。`ThemeProvider._sync_app_palette` 改为读 `background` / `foreground`。
4. **原地改写。** `HEROUI_COLORS`、`RADIUS` 原地改；其余取值存进统一的主题取值模块。组件运行时读，不在 import 时缓存。
5. **阴影缓存。** `setup` 应用阴影配置时清空缓存，并预热当前主题三档。
6. **晚调用警告。** `theme_values` 模块记录"是否已被读取过"；已读取后才调用 `setup`，说明已有组件按旧值画过了，给一次警告：已有组件不会刷新。不用 `ThemeProvider` 的注册数判断，它只统计 `theme="auto"` 的组件。
7. **显式优先。** `setup` 配的是组件外观默认值；用户在组件上显式传的颜色、字号（如 `Text(color="#ff0000")`）永远优先。

### 实现方式上的补充

- **字号怎么"跟着配置变"：** 预设里的字号字面量已改成档位值，`themes/__init__.py` 在导入时调用 `theme_values.bind_font_slots` 扫描所有预设，把字号槽位绑定到档位；`font_size` 变化时原地改写这些槽位，组件代码不用改。预设里若出现不在五档上的字号，导入时直接报错（防止以后又写出零碎字号）。绑定共 142 个槽位（126 条加 DateInput 等由 Input 派生出的拷贝）。
- **阴影层的本体矩形：** `ShadowLayer` 默认以目标控件的矩形为本体；Card 的外壳可能被父布局拉得比内层 `_content` 宽，所以支持"本体矩形提供者"，阴影贴着可视卡片；Image 用"内缩"，避开模糊副本的留白；Table 的阴影只包内部 Card，不包 top / bottom 附加内容。
- **`ShadowController`：** 目标没有父控件时不创建阴影层（避免凭空产生顶层窗口），目标换父控件时阴影层自动跟随。
- **晚调用检测：** 基础设施自己读主题取值（ThemeProvider 同步调色板、`setup()` 预热阴影）不算"组件已创建"，不会误触发警告。
- **对比度警告：** 只检查用户改动过的颜色，默认值不检查（success 白字 2.18:1、danger 4.11:1 是 HeroUI 沿用的外观）。
- **`mono_family`：** 配置后 `mono_family()` 直接返回该字体；`mono_family(font_path=...)` 显式传路径时仍以显式为准。

### 附带修复：弹出层不能伸出应用窗口

不属于主题定制，但同一轮处理。Popover、Tooltip、Dropdown、Select、Autocomplete、Slider 浮标都是独立的顶层窗口，原来只按屏幕边界判断翻转，所以窗口小于屏幕时，弹出层会伸到应用窗口外面。

- 新增 `_shared/overlays/bounds.py`：边界 = 触发控件所在窗口的客户区内缩 8px，再与所在屏幕可用区求交；浮层里再开的浮层沿 `_hs_host_window` 回到最外层应用窗口。
- 定位按浮层**可见主体**（不含阴影留白）判断：先试指定方向，放不下且允许翻转时试反方向，两边都放不下取越界更少的一边，仍越界就整体推回窗口内；带箭头时箭头反向偏移，仍指向触发控件。
- Select / Autocomplete 原来刻意 `allow_flip=False`（"必须优先向下"）。现在改为允许翻转，但保持优先向下：下方够放一个最小列表（80px）就留在下方、列表变矮靠滚动；下方比这还小才翻到上方。Dropdown 原本就能翻转，高度上限改按窗口内上下较大的一侧算。
- `available_height_below` 沿用旧名，语义变为"窗口内可用高度"。
- 测试：`tests/components/test_popup_bounds.py`（新）；同步 Select / Autocomplete 的 `_allow_flip` 断言与 `available_height_below` 的测试。
- 已知限制：Select / Autocomplete 的列表高度只在打开时按窗口空间算一次，打开后再拖动窗口大小，弹出层会按新边界被推回窗口内，但列表高度不会重算。

### 用户反馈后的修复（2026-11-16）

- **阴影被紧凑容器裁掉：** 第一版把阴影层挂在目标的直接父控件下，而 Image 示例里“图片 + 说明文字”被一个紧凑容器包着，阴影被裁得几乎看不见（sm / md 的可见部分全在容器外面）。改为挂到最近的裁剪边界（滚动区视口或窗口），叠在目标上方，并监听目标到边界之间所有祖先的移动 / 缩放 / 显隐（滚动区滚动时被移动的是内容控件）。同时补上了暗色主题的 1px 内描边（之前阴影层只画了外阴影）。
- **Pressable / Hoverable Card 点外面也触发：** 原来 `setFixedWidth` 等被代理到内层 `_content`，外壳被布局拉宽后，多出来的那块也响应点击。阴影不占位后代理已无意义，已删除，外壳与本体恒等大。
- **Dropdown 同时开两个、触发时灵时不灵：** 工作区里有一处没做完的“浮层阴影留白点击穿透”改动（`HitThroughMixin`），要求使用方实现 `_body_global()`，但 Popover / Tooltip 都没实现，点击外部时抛 `NotImplementedError`，浮层不会被关闭，窗口的命中测试也跟着出错。已补上实现（基于 `_body_local()`），并把 `HitThroughMixin` 挪到 `QWidget` 前面，避免它的占位实现盖住真实实现。这个“穿透”改动本身是为了解决我把浮层阴影留白放大（md 18 → 48px、lg 121px）后，透明留白吞点击的问题。
- **Invalid 复选框的蓝色：** 不是 bug。截图里是点击后选中动画的中间帧（填充不透明度约 65%）；最终状态是纯蓝实心，与官方 HeroUI 一致（`isInvalid` 只改边框和文字，选中填充盖住边框）。

### 弹层越出窗口的最终做法（2026-11-16，用户选定 A + C 兜底）

- 可用区域 = 触发控件所在窗口的客户区 ∩ 所在屏幕（`bounds.popup_area`）；越界量用 `bounds.overflow` 按弹层**可见主体**（不含阴影与箭头留白）计算。
- A（翻转）：指定方向放不下且允许翻转，就试相反方向，完整放得下就用它。
- C（切断兜底）：两边都放不下，取越界更少的一边，窗口外的部分由 `clip_to_host` 用 mask 裁掉，弹层不会伸出应用窗口。
- Select / Autocomplete 重新开启翻转（`allow_flip=True`），仍然优先向下：下方够放最小列表（80px）就留在下方、列表靠滚动；下方更小才翻到上方，此时高度按上下较大的一侧算。Dropdown 同理，按指定方向那一侧够不够 80px 来决定。
- 之前“推回窗口内 + 箭头反向偏移”的方案已被替换，`host_bounds` / `shift_into` / `shift_arrow` 不再存在。
- Slider 浮标固定在拇指上方，不翻转，只做切断。

### Pressable Card 点击文字不触发（用户反馈）

`Card(is_pressable=True)` 里插入的 `Text` / `QLabel` 会消费掉鼠标按下事件，卡片外壳收不到，水波纹和 `pressed` 信号都不触发（只有点空白处才行）。改为在内容子树上装事件过滤器：子控件照常处理自己的事件（文字仍可选中），卡片同时收到转发来的按压；同一事件沿父子链传播多次时用一次性标记去重，每个点击只加一个波纹。新增子控件通过 `ChildAdded` 事件自动装上过滤器。逻辑放在 `components/card/_press.py`，`card.py` 保持在 800 行以内。

### 组件宽度统一（2026-11-16）

不属于主题定制，但同一轮处理。完整约定与全部组件总表见 [width.md](width.md)。

- 输入类（Input / Textarea / NumberInput / DateInput / TimeInput / Select / Autocomplete / DatePicker）：预设里的 `min_width` 改名 `default_width`，只当 `sizeHint`（新增 `_shared/fields/width_mixin.py` 的 `SuggestedWidthMixin`），外框用 `release_width_floor` 解除下限；删除 Input / DateInput 拦截 `setFixedWidth` 等三个方法与 `_user_width_locked`，以及 Select 的设宽转发。顺带修好：Textarea 设宽被无视、Autocomplete 与 DatePicker 设窄宽度时内层外框超出外壳。
- NumberInput 不再有建议宽度，删除 `NUMBER_INPUT_MIN_WIDTHS`（公开导出，属于不兼容改动）。
- 内容型（Button / Chip / Checkbox / Radio / Switch / Badge / Pagination / Tabs / InputOtp）水平策略统一为 `Maximum`，对齐官方 `inline-flex` / `max-w-fit`；这些组件的 `minimumSizeHint` 等于 `sizeHint`，所以仍不会被压窄。Button 原为 `Minimum`（会被布局拉宽）。Badge 竖排不再被拉满、头像不再居中错位。
- Select、Accordion 补 `full_width=True`；Autocomplete 改 Expanding；DatePicker / DateRangePicker 的 `full_width=True` 现在真的是 Expanding；Slider 沿滑动方向建议长度 200。
- 顺带修：`ShadowController.eventFilter` 在目标 Python 包装先被回收时不再抛异常。
- 测试：新增 `tests/shared/test_width_contract.py`；同步 `test_number_input.py`、`test_date_input_widget.py`。已写未跑。
- 已知变化：横排并排两个 Button 不再各被拉到一半宽，各自内容宽（官方横排也是如此）。

### 宽度数字有来历（2026-11-16）

查证后发现各组件的宽度数字来路不一：有照抄官方的，有自己拍的，也有抄错的（Button 最小宽实测 60 / 84 / 106，官方是 64 / 80 / 96）。原则：每个数字只能是三类之一——官方有则照抄；官方没有但 Qt 必须补则全库只用一个；其余按内容算。详见 [width.md](width.md) 末节。

- **统一建议宽度 320**：新增 `themes/width.py` 的 `SUGGESTED_WIDTH`。来源是官方输入类示例里 `max-w-xs`（= 320px）出现 139 次。输入类（含 NumberInput、DateInput、TimeInput、DatePicker）、Slider、Progress 共用，不再按 sm / md / lg 分档；预设里的 `default_width` 字段、DateInput 的"按日期文字估算"、NumberInput 的无建议宽度都删了。
- **Button**：最小宽 60 / 84 / 106 → 64 / 80 / 96（QSS 里要扣掉左右留白和边框，因为官方 `min-w` 是 border-box）；lg 左右留白 20 → 24（官方 `px-6`）。只有文字很短的按钮会变。
- **Dropdown**：菜单最小宽 180 / 200 / 220 → 固定 200（官方 `min-w-[200px]`，不分档）。
- **Chip**：左右留白 8 / 10 / 12 → 8 / 12 / 16（官方 base 与 content 的 padding 叠加）。
- **删写死的数**：Tabs 标签最小宽 36 / 44 / 52；Table 复选框列宽 36 / 40 / 44 改为"方框宽 + 左右留白"（36 / 44 / 52）。
- **Radio 卡片上限**：260 / 300 / 340 → 统一借用 320，标为 Qt 补丁。
- Select / Autocomplete 打开时弹层宽度改取输入框实际宽度（输入框已显示时），不再取 `max(实际宽, sizeHint)`，否则用户把输入框设窄后弹层仍是 320。

### Toast 混用不同阴影档位时错位（用户反馈，2026-11-16）

先点 sm 再点 lg 的 Toast，卡片宽度不一、位置错开，而且 lg 离窗口边缘比 sm 更远。三个原因叠在一起，都出在我把阴影留白改成"随档位变化"（sm 18 / md 48 / lg 121）之后：

- **各画各的留白：** Region 按"所有卡片留白的最大值"统一算卡片宽度和 x，卡片自己绘制却用自己档位的留白，sm 卡片的可见主体被撑宽、错位。改为 Region 把统一留白下发给每张卡片（`set_pad_override`），卡片的 `own_pad()` 仍是它自己档位的值，大卡片退出后其余卡片自动恢复。
- **内容悬空：** 内容布局的外边距只在构造时按当时的留白设置一次，留白变了背景跟着变、图标和文字不动。留白变化（含 `set_shadow`）时现在会重设（`_apply_root_margins`）。
- **横向离边缘更远：** 竖向已经按"可见主体"对齐窗口边缘，横向却按卡片控件对齐，留白越大离边越远。`_x_for` 现在扣掉留白，6 个方位下任何档位的可见主体到窗口边缘都是 `margin`（16px）。

已知取舍：同时存在 lg 卡片时，所有卡片的透明留白都是 121px，这块透明区域会挡住它下面宿主控件的点击；只有 sm 时是 18px。这是"卡片挂在宿主窗口、留白是控件一部分"这个结构带来的，没有处理。

### Toast 拖动的是别的卡片（用户反馈，2026-11-16）

展开状态下，卡片控件含透明的阴影留白（sm 18px，lg 121px），相邻卡片的留白会盖住别的卡片的可见区域，鼠标按在可见主体上，事件却被层级更高的那张卡的透明留白接走，拖动的就是它。top 类方位是上面的新卡盖住下面老卡的上部，bottom 类相反。真实点击扫描：旧代码 6 方位 × 2 档位共 72 处点错。

修法：卡片收到按下事件时先判断点是否在自己的可见主体内，不在就找真正被点中的那张卡，拖拽转交给它（移动、释放事件也转交）；点在谁的可见主体里都不是的纯透明区，忽略。修复后同样的扫描 0 处点错。

取舍：这只修了拖拽。卡片的透明留白仍然会挡住它下面宿主控件的点击（点透明区时事件被忽略，不会传给卡片下面的控件），要彻底解决需要像弹层那样做命中穿透。
